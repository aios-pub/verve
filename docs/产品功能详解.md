# Verve 产品功能详解

本文档面向使用者，系统介绍 Verve 的产品定位与各项功能模块——它们**能做什么、
解决什么问题、典型怎么用**。如果你想知道某个功能背后的技术实现，请参阅其它专题
文档；本文只讲产品价值与使用方式。

---

## 一、产品定位：为什么要做 Verve

Verve 是一个**离线优先、一站式开发者工作台**。它的出发点是一个再普通不过的
痛点：

> 一次完整的后端排障，你可能要在 Postman 里发请求、切到 Termius 看 SSH 日志、
> 跳到 Dashboard 看 Docker/K8s、再开一个 JSON 格式化器贴返回值、顺手编辑一下
> `/etc/hosts` 做联调……光是把上下文在这些软件之间来回搬运，就耗掉了大半个
> 下午。

这些高频工作流原本散落在十几个软件里，带来三个核心问题：

1. **工具切换成本高**：每个软件都要登录、配置、找窗口，上下文在切换中丢失。
2. **内存被 Electron 吃光**：Postman、Termius、Notion 全是 Electron，每个吃
   几百 MB，开齐一套，16G 内存见底。
3. **数据割裂**：API 定义在 Postman、笔记在 Notion、Mock 配置在另一个服务，
   它们之间无法互通。

Verve 的主张是：把这些高频工作流**收进一个原生窗口**，用 Rust + GPU 渲染，做到
启动不到 1 秒、常驻内存 100MB 以内、全程流畅。它具体覆盖以下能力：

| 能力域 | 替代/整合的工具 | 典型场景 |
| --- | --- | --- |
| **API 开发与调试** | Postman / Apifox / Swagger | 多协议请求、环境变量、Mock、接口管理 |
| **SSH 运维** | Termius / iTerm | 终端 shell、`docker logs`/服务日志跟踪、跳板机、断线重连 |
| **Docker 容器管理** | Docker Desktop | 容器/镜像列表、日志跟踪、`exec` 进容器 |
| **Kubernetes 运维** | k9s / Lens | pods/namespace、日志、进容器、端口转发 |
| **知识沉淀** |  Notion | Markdown 笔记 |
| MarkDown编辑 | Typora / MarkText | Markdown编辑 |
| **实用工具** | JSON 格式化器 / hosts 编辑器/流量抓包 | JSON、Hosts、流量抓包 |
| 压测/自动化测试 | Apache JMeter | 接口压测 |
| 磁盘迁移 | Carbon Copy Cloner | 磁盘不足时将某文件夹下内容迁移至外置SSD建立软链接 |

一句话：**Verve 把"一个后端开发者每天都要碰的那些事"装进了一个原生窗口**，让你
少开几个软件、少切几次窗口、少丢几次上下文。

## 二、功能全景图

Verve 的功能不是孤立堆砌的，而是围绕一条**完整的开发工作流**串联起来的：

```
接口开发 → 流量/Mock → 服务器排障 → 性能测试 → 文档沉淀 → 协作同步
   │           │            │            │           │          │
   ▼           ▼            ▼            ▼           ▼          ▼
 API 调试    抓包代理     SSH/Docker   压测/自动化   笔记       文档分享
 多协议      本地 Mock     /K8s         测试套件    Markdown   Git 同步
 环境变量    规则匹配     日志跟踪                  PDF/JSON   跨机
```

后续章节按这条主线展开。左侧的活动栏（Rail）是功能的总入口，共 17 个入口，可以
自定义显示、隐藏和排序。

## 三、API 开发与调试（核心）

这是 Verve 最核心的功能域，定位为 Postman / Apifox 的原生替代。

### 3.1 多协议支持

不止 HTTP，Verve 把开发者常碰的几种协议都收了进来：

| 协议 | 适用场景 |
| --- | --- |
| **HTTP/HTTPS** | 最常用的 REST 接口调试，支持 GET/POST/PUT/DELETE/PATCH 等全方法 |
| **gRPC-Web** | 调试前端直连的 gRPC-Web 接口（浏览器侧 gRPC） |
| **WebSocket** | 调试长连接接口，如实时推送、IM、协同 |
| **SSE**（Server-Sent Events） | 调试服务端事件流，如 AI 流式输出、通知推送 |
| **TCP** | 调试裸 TCP 协议、自定义二进制协议 |

这意味着你不用为了调一个 WebSocket 再开一个专门的工具。

### 3.2 接口组织：树形管理

接口不是扁平列表，而是**项目 → 文件夹 → 接口**的树形结构：

- 一个**工作区**下可以有多个项目，项目之间相互独立。
- 每个项目下用**文件夹**分层组织接口，文件夹可任意嵌套。
- 支持拖拽排序、跨文件夹移动、复制接口、重命名、删除。
- 点击接口即在一个新的标签页打开，可同时打开多个接口来回切换。

这种组织方式适合从几十到上千个接口的规模，配合搜索和定位功能，大型接口库也能
快速找到目标。

### 3.3 环境变量与目录级继承

环境变量解决"同一套接口，不同环境（开发/测试/预发/生产）"的问题：

- 每个**项目**可以定义多套**环境**（如 `dev` / `staging` / `prod`），每套环境是一组
  键值对。
- 接口里用 `{{base_url}}`、`{{token}}` 这样的占位符引用变量，发送时自动替换。
- 切换环境只需点一下下拉框，所有接口的变量一起切换。

更强大的是**目录级继承**：

- 你可以在**文件夹**层定义 `base_url`、通用 `headers`、`params`、`variables`，
  该文件夹下的所有子接口**自动继承**这些配置。
- 子接口可以进一步覆盖或补充。
- 这样做的好处是：同一个业务的几十个接口，不用每个都重复写 `Authorization`
  header 和 base\_url，改一处全生效。

### 3.4 请求编辑

请求编辑面板覆盖了实际开发中会遇到的全部要素：

- **Body**：支持 JSON / 表单 / 文件上传 / 原始文本 / GraphQL 等多种类型。
- **鉴权（Auth）**：Bearer Token / Basic Auth / API Key（Header 或 Query）/ 无，
  选中即自动注入，无需手动拼 header。
- **路径变量（Path）**：用于 `/api/users/:id` 这类路径模板，填好后自动替换。
- **Query 参数**、**Headers**、**Cookie** 都以可启停的键值行编辑，可整体禁用。
- **Pre-Request / Post-Request 脚本**：用内置脚本引擎在发送前后执行逻辑，可用于
  动态签名、提取 token、断言响应、串联流程。

### 3.5 响应查看

响应区提供多个视图，从不同角度审视一次请求的结果：

- **实时响应**：展示状态码、耗时、响应体（JSON 自动格式化、可折叠）。
- **Headers**：响应头列表。
- **Cookie**：Set-Cookie 解析。
- **示例（Example）**：把当前响应存为参考示例，之后可与 Mock 联动。
- **实际请求**：展示最终发出去的完整请求（含变量替换后的真实 URL/body），方便
  复制为 cURL 或排查"我到底发了什么"。
- **控制台**：脚本输出的日志。

### 3.6 历史记录

每一次发送都会进入历史记录，按时间倒序排列。点开任意一条历史，可以一键把当时的
请求重新载入编辑器，无需重新填一遍——排查"昨天那个请求是怎么发的"特别有用。

### 3.7 导入导出：与现有生态互通

不必从零开始重建接口库：

- **导入**：支持 Postman v2.1、OpenAPI 3、Swagger 2.0、Apipost 格式，也支持粘贴
  cURL 命令直接生成接口。
- **导出**：可把整个项目或单个接口导出为上述格式，方便和仍用 Postman 的同事
  协作，或交付 API 文档。

## 四、流量抓包与本地 Mock

### 4.1 HTTP 抓包代理

Verve 内置一个本地 HTTP 代理，把浏览器或客户端的请求导向它，即可在 Verve 里实时
看到所有经过的请求与响应：

- 适合排查"前端到底发了什么""第三方 SDK 请求了哪些地址"。
- 配置方式：启动代理后，把系统或浏览器代理指向 `127.0.0.1:<端口>`。
- 适用范围：明文 HTTP 流量（HTTPS 抓包需额外证书配置，当前版本以明文为主）。

抓到的请求可以直接转存为接口，纳入项目管理，实现"抓包即建档"。

### 4.2 本地 Mock 服务器

联调时后端接口没好、或想测试前端的各种异常分支，Mock 服务器就派上用场：

- **规则匹配**：支持精确匹配、前缀匹配、正则匹配三种方式，覆盖从单接口到整组
  路由。
- **模板变量**：响应体里可用 `{{mock.request.*}}` 引用入参，动态生成响应。
- **一键生成**：对于项目里还没配 Mock 的接口，可以一键生成默认 Mock 规则。
- **即时生效**：在 UI 里改完 Mock 配置，无需重启服务器，下一次请求就用新规则。

Mock 与上面的接口管理是联动的——接口的 Mock 标签页和 Mock 服务器共享同一套规则。

## 五、服务器与容器运维（Pro）

这是 Verve 区别于普通 API 客户端、真正走向"一站式"的关键部分。它把开发者排障
服务器时最常用的几样东西——SSH、Docker、K8s——整合进了同一个窗口。

### 5.1 SSH 终端

定位为 Termius 的原生替代，覆盖日常服务器排障的全部需求：

- **多标签**：同一主机可开多个会话，不同主机之间用卡片或标签切换。
- **跳板机/堡垒机**：支持配置跳板链，内网主机可通过堡垒机穿透连接，无需额外
  工具。
- **断线自动重连**：网络抖动、休眠唤醒导致的断线会自动重连（最多重试若干次），
  配合错误提示判断是否需要手动介入。
- **真彩终端体验**：完整支持 ANSI 16 色 + 256 色调色板，`vim`/`htop`/`tmux` 等
  全彩程序显示正常；中日韩等宽字符正确对齐，不会被错位切成乱码。
- **选中即复制 / 粘贴**：和原生终端一致的交互习惯。
- **两种用法**：既可开交互式 shell 做操作，也可常驻一条 `docker logs -f` 或
  `tail -f` 持续跟踪服务日志——把终端当日志面板用。

**凭证安全**：密码和私钥口令存在加密保险库里，主机配置文件里不含明文密钥，且
**不会弹出 OS 钥匙串授权窗口**（采用设备密钥封装，详见《安全机制》文档）。

### 5.2 文件传输

- **SFTP 浏览器**：在终端旁开一个文件浏览器，可视化浏览远端目录、查看大小权限，
  拖拽即可上传下载。
- **ZMODEM（rz/sz）**：在远端执行 `rz`/`sz` 时，Verve 自动接管传输，弹出保存
  对话框或选择本地文件发送——和经典 SecureCRT/Xshell 的体验一致，无需手动开
  SFTP。

### 5.3 端口转发

- 支持**本地端口转发**（把远端端口映射到本地）、**远程端口转发**。
- 每个转发规则可设置**开机自启**，连上主机即自动建立。
- 转发状态在面板里实时可见，随时启停。

典型用法：把远端 MySQL 的 3306 映射到本地，用本地的 DataGrip 连"localhost"访问
远端数据库，无需公网暴露。

### 5.4 Docker

Docker 面板把常用的容器操作可视化，省去记命令：

- **容器列表**：查看运行/停止状态、镜像、启动时间，支持启动/停止/重启/删除。
- **镜像管理**：列出本地镜像、清理悬空镜像（prune）。
- **日志跟踪**：对任意容器开 `docker logs -f`，实时滚动输出，支持语义高亮
  （时间戳、ERROR/WARN 着色）。
- **进容器**：一键 `docker exec -it` 打开 shell，排查容器内问题。
- **远程 Docker**：远端服务器的 Docker daemon 可通过已配置的 SSH 主机建立隧道
  访问——管远程 Docker 像管本地一样。

### 5.5 Kubernetes

K8s 面板定位为 k9s / Lens 的轻量替代：

- **导入 kubeconfig**：从默认 `~/.kube/config` 加载，或导入额外的 kubeconfig、
  手动添加集群。
- **切换 context / namespace**：下拉切换，无需手敲 `kubectl`。
- **Pods 列表**：查看状态、重启次数、所在节点。
- **日志跟踪**：对任意 pod 开 `kubectl logs -f`，支持指定 container。
- **进容器**：`kubectl exec` 进入 pod 排障。
- **端口转发**：把 pod 端口映射到本地，配合本地工具调试。

排查"某个 pod 为啥重启"这种问题，从切换 namespace 到看日志全程不用离开 Verve。

## 六、性能测试与自动化测试（Pro）

### 6.1 压力测试

想知道接口扛不扛得住、延迟怎么样，压测面板直接给你答案：

- **可调参数**：并发数、总请求数或持续时间、目标 QPS、超时时间。
- **开关项**：keep-alive、是否跟随重定向、HTTP/2。
- **目标选择**：直接从项目接口树里选要压的接口，继承其环境变量与鉴权。
- **结果呈现**：总请求数、成功/失败数、RPS、延迟分位数（P50/P90/P99/最大）、
  延迟直方图、状态码分布。
- **场景模式**：可编排多接口按顺序压测，模拟真实业务链路。

底层基于高性能压测工具 oha，单机即可打出可观压力。

### 6.2 自动化测试套件

比单次压测更进一步，自动化测试用于回归验证"改了代码有没有改坏接口"：

- **用例编排**：一个测试套件下包含多个测试用例，每个用例由若干**步骤**组成。
- **步骤类型**：
  - **发请求**：执行一个接口，可做断言（状态码、响应体字段、耗时）。
  - **条件分支（If）**：根据上一步结果走不同分支。
  - **循环（Loop）**：重复执行，支持固定次数或按集合遍历。
  - **等待（Wait）**：插入延时，等待异步处理完成。
  - **脚本（Script）**：自定义逻辑，灵活处理。
- **变量提取与传递**：从某一步的响应里提取值（如登录返回的 token），存为变量，
  后续步骤用 `{{token}}` 引用——实现"登录→下单→查询"的完整链路验证。

适合在每次发版前跑一遍，确保核心链路无回归。

## 七、知识沉淀与文档工具

排障和开发过程中产生的笔记、文档、参考材料，Verve 也提供了一组工具来沉淀，不必
再开 Notion 或 Typora。

### 7.1 Markdown 笔记

- 内置一个**树形笔记库**，可以建多层笔记、置顶重要笔记、拖动调整层级。
- 采用**所见即所得的块编辑器**（类似 Notion 的块式编辑），支持标题、列表、代码
  块、引用、表格、待办等，写完即是最终排版，无需在"编辑/预览"间切换。
- 支持代码语法高亮、LaTeX 公式、Mermaid 流程图。

笔记随工作区一起持久化、一起跨机同步。

### 7.2 独立的 Markdown 编辑器

除了内置笔记库，Verve 还能像 Typora / MarkText 一样**直接打开磁盘上的 `.md`
文件**：

- **命令行打开**：`verve path/to/note.md` 即可在 Verve 中打开该文件编辑。
- **双击打开**（macOS）：在 Finder 里双击 `.md` 文件，或拖到 Dock 图标上，自动
  用 Verve 打开。
- **多标签**：可同时打开多个文件，各自独立标签页。

这样 Verve 既能管"应用内的笔记库"，也能当日常的 Markdown 编辑器用，写 README、
技术文档都很顺手。

### 7.3 PDF 查看与编辑

内置 PDF 阅读与编辑能力，排障时截取的日志、交付的文档，不必再装专门的 PDF 软件。

### 7.4 JSON 格式化

每个开发者都缺不了的工具：

- 左侧粘贴原始 JSON，右侧立即渲染为**可折叠的树**。
- 大对象（超过阈值）默认折叠，避免一展开卡死界面。
- 支持展开/折叠全部、复制某个值的路径或内容、多种格式化选项。
- 自研的虚拟化渲染，即便是几 MB 的大 JSON 也能流畅滚动。

### 7.5 Hosts 管理

联调时频繁改 `/etc/hosts` 把域名指向不同机器，是后端常见操作：

- **多档案（Profile）**：维护多套 hosts 配置，按需启用/禁用，不必反复增删行。
- **环境绑定**：一个 hosts 档案可绑定到某个环境，只在切到该环境时生效。
- **两种应用方式**：
  - **虚拟覆盖**（推荐）：只对 Verve 自身发出的 HTTP 请求生效，\*\*无需管理员
    权限\*\*，不影响系统其它程序。
  - **写入系统 hosts**：真正改写 `/etc/hosts`，全局生效，需要管理员权限提权。

## 八、团队协作与跨机同步

### 8.1 文档分享

需要把某个接口或整个项目交给同事看（比如让前端对照联调），不必让对方装 Verve：

- **分享粒度**：可分享单个接口，也可分享整个项目。
- **本地局域网分享**：生成一个可访问的 HTML 页面和二维码，同网段同事扫码或访问
  URL 即可查看，无需账号。
- **云端分享**：通过自建的 `verve-server` 推送到公网，跨网段也能访问。
- **访问控制**：可设置访问密码、有效期、可见字段，控制谁能看、看多久、看哪些。
- **分享内容**：接口的方法、URL、参数、请求/响应示例、Mock 等，按需选择展示。

### 8.2 Git 跨机同步

Verve 把"把工作换台电脑也能接着干"做成了开箱即用：

- **整个数据目录即一个 Git 仓库**：所有项目、环境、笔记、配置默认纳入版本管理。
- **工作区 = 分支**：每个工作区对应一个 Git 分支，切换工作区即切分支，互不干扰。
- **自动提交 + 定时同步**：编辑后自动提交（可配置开关），并按设定间隔自动 push/pull，
  换台电脑 pull 一下就是最新状态。
- **分支管理**：在项目管理面板里可视化地建分支、切分支、合并、解决冲突。

这让"公司电脑和家里电脑的接口库保持一致"变得零成本，且所有改动都有 Git 历史
可回溯。

## 九、系统实用工具

### 9.1 磁盘目录迁移（relocate）

当磁盘空间紧张，想把某些大目录（如 Docker 镜像、npm 缓存、Xcode 衍生数据）迁到
外置盘时，手动迁移容易出错。Verve 的"磁盘迁移"功能提供安全的引导式迁移：

- **扫描家目录**，智能识别可迁移的类别（缓存、容器数据、开发依赖等）。
- **风险分级**，标注哪些目录迁移安全、哪些有风险。
- **一键迁移 + 回滚**：迁移出问题时可一键回滚到原状。

详见专题文档《relocate 磁盘目录迁移模块》。

## 十、个性化与设置

### 10.1 主题

内置 **22 个精选主题**，包括 Catppuccin、Gruvbox、Tokyo Night、Solarized、
Flexoki、Everforest 等流行配色，一键切换。支持亮/暗模式切换，编辑器配色随主题
联动。

### 10.2 语言

中英双语界面，默认中文。可在设置里切换，切换后立即生效。

### 10.3 全局参数

除了项目级的环境变量，Verve 还有**全局**的 Cookies / Params / Headers /
Variables 管理器——这些参数对所有项目的所有接口都生效，适合放那些跨项目通用的
配置（如全局追踪 header、公共 token）。

### 10.4 活动栏定制

左侧的活动栏（Rail）可以自由定制：隐藏你用不到的入口、拖动调整顺序，让界面聚焦
在你真正需要的功能上。

### 10.5 快捷键

常用操作有全局快捷键（macOS 为 `cmd-*`，其它平台为 `ctrl-*`），例如：

- 发送请求、保存工作区
- 新建接口、新建文件
- 打开 Markdown 文件

WYSIWYG 编辑器还支持自定义键位重绑。

### 10.6 更新检查

启动时静默检查 GitHub Releases，有新版本会在标题栏提示；手动检查则弹出通知，
引导你去下载新版本（`.dmg` / `.deb` / `.msi`）。

## 十一、版本与定价

Verve 分为两个版本，覆盖不同人群的需求。

### 社区版（Community Edition）

- **免费开源**，采用 AGPL-3.0 协议。
- 面向个人开发者的日常 API 工作，**完全够用**，覆盖：

| 功能 | 社区版 |
| --- | --- |
| HTTP 多协议调试 | ✅ |
| 接口管理 / 环境变量 / 目录继承 | ✅ |
| 流量抓包 | ✅ |
| 本地 Mock | ✅ |
| JSON / Hosts 工具 | ✅ |
| 本地文档分享 | ✅ |
| Git 跨机同步 | ✅ |
| 主题 / 双语 / 全局参数 | ✅ |

### Pro 版

- **赞助制**（早鸟价更优惠），闭源。
- 在社区版基础上，增加面向**服务器排障与深度测试**的能力：

| 功能 | Pro 版额外提供 |
| --- | --- |
| SSH 终端（shell / 日志 / 跳板机） | ✅ |
| SFTP 文件传输 / ZMODEM | ✅ |
| 端口转发 | ✅ |
| Docker 容器管理 | ✅ |
| Kubernetes 运维 | ✅ |
| 压力测试 | ✅ |
| 自动化测试套件 | ✅ |
| Markdown 笔记 / 独立 Markdown 编辑器 | ✅ |
| PDF 查看/编辑 | ✅ |
| 云端文档分享（verve-server） | ✅ |

**选择建议**：如果你主要做接口调试和本地开发，社区版即可；如果你经常要登录
服务器排障、管 Docker/K8s、做性能或回归测试，Pro 版能把这些事都收进一个窗口，
显著减少工具切换。

## 小结

Verve 的产品逻辑很简单：**开发者每天的高频操作，不该被切碎在十几个软件里**。
它用一套原生、低占用、可离线、可同步的工具，把 API 调试、流量与 Mock、服务器和
容器运维、性能与自动化测试、笔记与文档、协作同步整合到了一起。

无论你只用社区版做接口调试，还是用 Pro 版把它当成主力工作台，目标都是同一个：
**少开几个软件，多专注一点问题本身**。
