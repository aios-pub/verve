# 安全与凭据

本文档说明 Verve 如何存储敏感信息（SSH 密码、私钥口令等），为何**不会**弹出
OS 钥匙串授权窗口，以及该设计与其他 SSH 客户端的对比。

---

## 概述

Verve 的一项核心原则：**密钥绝不以明文形式写入主机配置文件。** 主机列表
（`~/.verve/ssh_hosts.json`）只保存非敏感的连接元数据（地址、端口、用户名、认证
方式）。每个密码和私钥口令都单独存放在一个**加密保险库（vault）**里，用设备专属
密钥封装。

设计目标是"Termius 式"的体验：**无需记忆主密码，也没有每次访问都弹出的 OS
钥匙串授权框** —— 同时保证密钥在静态存储下加密、并按 OS 用户隔离。

---

## 凭据如何存储

| 文件 | 用途 | 权限（Unix） |
|---|---|---|
| `~/.verve/ssh_hosts.json` | 主机连接元数据（不含密钥） | 默认 |
| `~/.verve/device.key` | 32 字节随机设备密钥 | `0600` |
| `~/.verve/ssh_vault.bin` | AES-256-GCM 加密的密钥集合 | `0600` |

工作流程：

1. 首次运行时，Verve 生成一个随机的 256 位**设备密钥**，写入
   `~/.verve/device.key`（Unix 下权限 `0600`，仅当前用户可读）。
2. 每个 SSH 密码 / 私钥口令作为一项存入**保险库**
   （`~/.verve/ssh_vault.bin`），用设备密钥经 **AES-256-GCM**（带认证的加密）
   加密。保险库文件格式为 `[12 字节 nonce][密文 + GCM tag]`。
3. 连接时，保险库在内存中解密一次（并缓存供本次进程后续使用），取出所需密钥，
   然后设备密钥被清零（zeroize）。

由于设备密钥从不离开本机，且保险库采用带认证的加密，只拿到
`ssh_hosts.json` 的攻击者一无所得；只拿到 `ssh_vault.bin` 而没有
`device.key` 也无法解密。

## 为何不需要主密码 / 不弹钥匙串

早期版本的 Verve（以及许多其他 SSH 客户端）把密钥存在 OS 钥匙串里。在 macOS
上这通常带来两个痛点：

- **每次访问都弹授权框。** macOS 钥匙串按"调用方应用的代码签名"来校验每条目
  的访问控制列表（ACL）。对于临时签名（ad-hoc）或频繁重新编译的应用（开源构建
  的常态），签名哈希（`cdhash`）每次构建都变，macOS 就认不出这是"同一个受信任
  的应用" —— 你点过的"始终允许"被遗忘，下次访问又弹窗。
- **主密码的繁琐。** 有些应用为了绕开钥匙串，用一个用户必须在启动时输入的主
  密码来加密保险库 —— 安全，但麻烦。

Verve 的设备密钥方案同时规避了两者：

- **不访问钥匙串** → 没有 ACL → 没有授权弹窗。永远没有。
- **没有主密码** → 设备密钥自动生成并以受保护文件形式存储，用户无需输入。

这与 Termius 等商业客户端的思路一致 —— 它们同样维护自己的加密存储，从不触发
OS 钥匙串弹窗。

## 各模块的凭据来源

| 模块 | 密钥存放位置 | 何时读取保险库 |
|---|---|---|
| **SSH**（密码 / 私钥口令） | 设备密钥加密的保险库 | 每次新建连接时（首次解密后缓存） |
| **Docker**（SSH 隧道模式） | 复用 SSH 主机的保险库密钥 | 仅在首次建立 SSH 隧道时（隧道按主机缓存） |
| **Kubernetes**（SSH 隧道模式） | 复用 SSH 主机的保险库密钥 | 仅在首次建立 API 隧道时（按集群缓存） |
| Kubernetes API 认证（token / 客户端证书 / 基本认证） | 明文存于 `~/.verve/kube_clusters.json` + 临时 kubeconfig | 不在保险库内 |
| Docker 本地 / TLS | 环境变量（`DOCKER_HOST`、`DOCKER_CERT_PATH` 等） | 不在保险库内 |
| Git token | 仅内存（从不落盘） | 不存储 |

> **说明：** Kubernetes API token 和 Git token **尚未**接入保险库 —— 它们要么
> 明文存储，要么仅保留在内存中。将其纳入保险库是后续工作。

## 安全考量

- **文件权限。** `device.key` 和 `ssh_vault.bin` 在 Unix 下以 `0600` 模式写入
  （仅属主可读写）。Windows 上由用户配置文件的 NTFS ACL 提供等价隔离。
  `~/.verve/` 目录以 `0700` 创建。
- **内存卫生。** 设备密钥使用后即 [`zeroize`](https://docs.rs/zeroize) 清零。
  解密后的密钥映射在进程内存中缓存（供本次 app 运行期使用），使保险库每次运行
  最多解密一次；该缓存不落盘。
- **加密。** AES-256-GCM 同时提供机密性和完整性（带认证的加密）。每次写入都
  生成新的随机 nonce，为磁盘上的密文提供前向保密。
- **信任边界。** 本设计可防范同机的其他非特权用户，以及主机配置文件丢失。它
  **不能**防范拥有 root/管理员权限或能物理接触已解锁会话的攻击者 —— 这类攻击者
  可以从磁盘读取设备密钥或转储进程内存。（通过 Secure Enclave 做硬件级保护是
  可能的未来增强方向。）

## 从早期基于钥匙串的版本迁移

如果你是从"将 SSH 密钥存在 OS 钥匙串"的旧版本升级，那些密钥无法被新的保险库
读取。编辑每个受影响的主机时重新输入一次密码 / 口令即可 —— 之后它就会被存入
加密保险库。你可以通过"钥匙串访问"（macOS）、"凭据管理器"（Windows）或
`secret-tool`（Linux）手动清理旧的钥匙串条目，搜索服务名 `verve.ssh`。
