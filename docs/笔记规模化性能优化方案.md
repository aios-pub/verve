# 笔记规模化性能优化方案

> 状态：**待决策**（未实现）。本文档为「笔记过大」（单条超长文档 + 笔记数量大）的性能优化蓝图，整合存储架构、组织模型等已定决策。
> 前置基础：笔记已改造为「每条一个 `.md` 文件 + YAML frontmatter」存储 + id→路径缓存（`save_note` 已 O(1)）。
> 行号基于 2026-08 当前代码，后续可能漂移，**以函数名/接入点描述为准**。

---

## 一、问题维度

「笔记过大」是两个独立瓶颈，主流项目分别应对：

| 维度 | 典型场景 | 压力点 |
|---|---|---|
| **单条笔记体积大** | 几千~上万行的超长文档 | 编辑器渲染、装饰管线、解析 |
| **笔记数量大** | 数千~数万条笔记 | 启动加载、内存、搜索、链接补全、侧栏 |

---

## 二、存储架构决策：C 思源模式（双重存储）

**决策**：`.md` 文件做权威存储 + `redb`（Rust 原生嵌入式数据库）做派生索引层 + `Tantivy` 做派生全文搜索。

| 层 | 角色 | 格式 | 进 git | 重建 |
|---|---|---|---|---|
| **`.md` 文件** | **权威存储**（笔记正文 + frontmatter 元数据） | 纯文本 | ✅ 进 git（可 diff/合并） | — |
| **`redb` 索引层** | 派生索引（块/元数据/反链/父子关系） | 二进制 KV | ❌ 不进 git | 从 `.md` 重建 |
| **`Tantivy` 搜索索引** | 派生全文搜索（倒排索引） | 二进制 segment | ❌ 不进 git | 从 `.md` 重建 |

**核心原则**：文件做权威（保可读/Git/外部编辑/无锁定，复用已完成的 `.md` 改造），数据库做派生索引（保查询性能/规模化），两者都要——避免「二选一」困境。

---

## 三、组织模型决策：不加目录类型

**决策**：保持 Notion/思源式的**页面嵌套模型**——每条 Note 有 `content`（正文）+ `parent_id` 组树，每个节点既是容器又可有正文。**不引入独立目录类型**。

**调研依据**：
- **Notion 式「页面嵌套」是被验证的更优模型**：Notion 的核心创新是「没有真正的文件夹，一切是嵌套页面」（[folder is also a page](https://www.reddit.com/r/ObsidianMD/comments/189yvkn/)）；思源同样「文档嵌套文档」
- **Obsidian 用户反向追求此能力**：大量插件（Folder Note、Nested Notes）和需求帖希望文件夹也能有正文（[Obsidian Forum: Folder Note](https://forum.obsidian.md/t/have-each-folder-be-automatically-associated-with-a-note-like-the-folder-notes-plugin/108760)、[Seeking Notion-like Pages](https://forum.obsidian.md/t/seeking-feature-enhancements-or-community-plugins-for-notion-like-pages-folder-note-in-obsidian/91534)）
- **纯文件夹深嵌套被诟病**：「My Obsidian vault was a mess until I stopped using folders」（[MakeUseOf](https://www.makeuseof.com/obsidian-vault-organization-without-folders/)）

**结论**：Verve 当前的页面嵌套本身就是优势，无需退步到传统文件夹模型。若未来「容器笔记空正文尴尬」成为痛点，再加「软目录」增强（Note 加 `kind` 标记，UI 表现为文件夹），而非引入独立 Dir 类型。

## 四、调研依据汇总

### 1. 存储四范式对比

| 范式 | 代表项目 | 主存储 | 索引层 | Git 友好 | 外部编辑 |
|---|---|---|---|---|---|
| **纯文件** | Obsidian / Foam / Zettlr | `.md` 文件 | 内存缓存 | ✅ | ✅ |
| **纯数据库** | Joplin / Trilium / Standard Notes | SQLite | 内置 FTS | ❌ | ❌（需导出）|
| **block + 数据库** | AppFlowy（Yjs CRDT）/ Notion | SQLite | 内置 | ❌ | ❌ |
| **双重存储** | **思源 SiYuan** | `.sy` JSON 文件 | SQLite（派生）| ✅ | ✅ |

### 2. 思源双重模型（本方案的理论依据）

- **文件层（权威）**：`.sy` JSON 文件——明文、可 diff、Git 友好，存块树结构（[思源文件系统介绍](https://zhuanlan.zhihu.com/p/647593068)、[存储设计](https://blog.csdn.net/m0_66090770/article/details/148545567)）
- **SQLite 层（派生索引）**：`blocks`/`attributes`/`refs`/`spans` 表——快速查询、搜索、反链、SQL API，**从文件重建**
- **导出 Markdown**：每个 block 预渲染 markdown，可干净导出

### 3. Logseq 文件→数据库迁移的教训（警示）

Logseq 从文件版（OG）转 SQLite 版（DB）的原因是文件模式「缺持久化 ID/时间戳/结构化数据，同步易丢数据、大规模卡」（[Why the database version](https://discuss.logseq.com/t/why-the-database-version-and-how-its-going/26744)）。但代价惨重：
- 迁移**有损且单向**（元数据导出 markdown 时丢失，回不去文件版）
- 大量用户**抗拒迁移**（[Is anyone planning to use OG indefinitely?](https://discuss.logseq.com/t/is-anyone-planning-to-use-og-version-indefinitely/35091)）
- 失去「直接编辑文件 / Git 版本控制」核心价值

**启示**：为数据库查询优势放弃文件存储会重蹈覆辙——思源证明**无需二选一**。

### 4. AppFlowy / Joplin 选纯数据库的理由（Verve 不适用）

- **AppFlowy** 用 SQLite + Yjs CRDT，唯一理由是**实时多设备协作**（[官方说明](https://forum.appflowy.com/t/...)）——Verve 不需要
- **Joplin** 用 SQLite + FTS5 是为同步/搜索/规模，但用户**不直接接触文件**

### 5. 组织三模型对比

| 模型 | 代表 | 「文件夹」有正文 | 评估 |
|---|---|---|---|
| 文件夹+文件 | Obsidian、Joplin | ❌ 纯容器 | 直觉，但深嵌套易乱 |
| **页面嵌套** | **Notion、思源、Verve** | ✅ 容器即页面 | 灵活，被验证更优 |
| 链接/标签 | Logseq、Roam | — | 网状，无层级 |

## 五、git 同步策略

**原则**：git 同步**权威数据**（`.md` 笔记），派生数据（索引）不进 git。

| 数据 | 进 git | 理由 |
|---|---|---|
| `.md` 笔记（权威） | ✅ | 纯文本，可 diff/合并，是用户的真实数据 |
| `redb` 索引（派生） | ❌ | 二进制；进 git 会仓库膨胀 + 冲突不可合并；可从 `.md` 重建 |
| `Tantivy` 索引（派生） | ❌ | 多 segment 二进制；同上 |
| `notes.meta.json`（UI 状态） | ✅（已有） | 小文本，可合并 |

**实现**：`.gitignore` 增加 `notes/index.redb`、`notes/tantivy/`（或集中到 `~/.verve/index/`）。首次启动/索引缺失时从 `.md` 自动重建。这与 Obsidian（`.obsidian/` 缓存不进 git）、思源、Joplin（FTS 表不进 git）的主流做法一致。

## 七、优化项（结合 redb / Tantivy）

### 优化 A（最高优先）：搜索 —— Tantivy 全文索引 + redb 元数据 + 防抖
**问题**：搜索每按键 O(n²)（`build_note_children` 递归 + `descendants_match` 每节点线性扫 store）+ 每篇 content `to_lowercase()` 克隆。

**方案**：
1. **搜索防抖**（200ms）
2. **Tantivy 全文索引**：索引每篇笔记的 title + content（中文用分词器，如 `tantivy` + 中文 tokenizer），笔记变更时增量更新。搜索走 Tantivy 查询（O(匹配数)）而非全扫描
3. **redb 元数据索引**：父子关系、标签、pinned 等结构化字段存 redb，搜索结果用 redb 过滤/排序（替代 `children_of`/`has_children` 线性扫）
4. 索引随 `.md` 变更自动维护（watcher 触发增量更新）

**收益**：每按键从 O(n²) + O(n×内容分配) → O(匹配数)，搜索体验质变。

### 优化 B（高优先）：父子 / 反链索引持久化到 redb
**问题**：`children_of`/`has_children`（`notes.rs:631-648`）每次线性扫 store；双链反链（计划中）也需索引。

**方案**：redb 存 `parent_id → [child_id]`、`id → [outlink]`、`id → [inlink]` 映射。笔记变更时增量更新（content 变更重扫该篇出链，title 变更更新 by_title）。

**收益**：树构建、反链查询 O(1)/O(度数)，替代线性扫。

### 优化 C（高优先）：惰性 content 加载
**问题**：`load()` 读所有 `.md` 全文进内存（content 全加载），启动慢、内存 O(总内容)。

**方案**：
- `load()` 只解析 **frontmatter**（title/parent/pinned/tags/时间戳），`content` 留空
- `select_note` 打开某笔记时才读该文件正文
- 侧栏树只需 frontmatter；搜索走 Tantivy（已索引 content）无需加载正文
- 内存从 O(总内容) → O(当前笔记内容)

**收益**：启动时间 + 常驻内存大幅下降。

### 优化 D（中优先）：笔记切换解析缓存
**问题**：每次 select_note 全量 `from_markdown` 解析（IME 限制无法复用编辑器实体——`notes_panel.rs:546-552`）。

**方案**（需评估 IME 影响）：后台预热——最近访问的 N 个笔记空闲时预解析，切换时复用解析中间结果（仍新建编辑器实体但跳过 parse）。或 LRU 缓存已解析块树（按 content hash）。

**收益**：切换响应更快。**风险**：IME 限制是 GPUI 特定问题，需 macOS 实测。

### 优化 E（中优先）：编辑器虚拟化健壮性 + 阈值下调
**问题**：`FULL_MOUNT_ROW_LIMIT=400`（>400 行才窗口化），且窗口化有黑屏 bug（`render.rs:2201-2228`），导致保守设 400，多数文档走全量渲染。

**方案**：下调阈值（如 150–200 行）+ 修健 row stride 估算（`render.rs:2229-2253`），消除黑屏 bug。

**收益**：超长笔记编辑/滚动流畅。**风险**：黑屏 bug 是既有脆弱点，需充分回归。

### 优化 F（中优先）：DocumentTree 增量更新
**问题**：每次结构编辑（缩进/移动/删除块）全量 DFS rebuild `VisibleTreeSnapshot`（`tree.rs:182-200`）。

**方案**：增量维护 snapshot——结构变更只局部更新受影响子树。

**收益**：大文档结构编辑更流畅。**代价**：DocumentTree 是移植核心，改动大、回归风险高。

### 优化 G（低中优先）：watcher 增量重载
**问题**：watcher 每个 notify 事件全量 `load_notes()`。开启 Git/Dropbox 同步时可能频繁触发。

**方案**：利用 notify 事件的具体 path，只重载被改文件，增量更新 store.notes + redb 索引 + file_paths，而非全量替换。

**收益**：同步场景不卡顿。

## 八、分阶段建议 + 量级阈值

| 量级 | 触发优化 | 说明 |
|---|---|---|
| **< 200 条** | 已完成（id→路径缓存） | 当前实现无感 |
| **200–1000 条** | 优化 A（Tantivy 搜索 + 防抖） | 搜索开始可感知卡顿，最高性价比 |
| **1000–5000 条** | + 优化 B、C（redb 索引 + 惰性 content） | 内存与启动压力显现 |
| **5000–10000 条** | + 优化 D、E（切换缓存/虚拟化） | 切换与大文档体验下降 |
| **10000+ 条** | + 优化 F、G（DocumentTree/watcher 增量） | 接近 Obsidian 实证上限 |

**建议执行顺序**：A → B → C → E → D → G → F。每阶段独立交付 + 验证。

|---|---|---|---|

## 十、关键设计决策

| 决策 | 选择 | 理由 |
|---|---|---|
| 存储架构 | **C 思源模式**（.md 权威 + redb 索引 + Tantivy） | 兼顾可读/Git/外部编辑 与 查询性能/规模化；思源验证可行；不推翻已完成工作 |
| 组织模型 | **不加目录**，保持页面嵌套 | Notion/思源式是被验证的更优模型；避免独立 Dir 类型的复杂度 |
| git 策略 | `.md` 进 git；redb/Tantivy 不进 | 权威数据进 git 可 diff/合并；派生索引进 git 会膨胀+冲突不可合并 |
| 搜索 | Tantivy 全文索引 + redb 元数据 + 防抖 | 替代 O(n²) 扫描；中文分词；增量维护 |
| 索引归属 | redb/Tantivy 是派生层，可从 .md 重建 | 无数据锁定；.md 始终是权威 |
| 数据库选型 | redb（纯 Rust 嵌入式）而非 SQLite | 用户要 Rust 原生；redb 无 C 依赖、事务性 |

## 十一、风险与缓解

- **索引一致性**：redb/Tantivy 必须在每个 `.md` 变更点增量维护，遗漏会漂移。建议统一在 mutation 后触发索引更新（或标 dirty 在空闲时重建），并加一致性测试（索引内容 == 从 .md 重算结果）。
- **优化 D（切换缓存）的 IME 风险**：GPUI 的 IME 绑定是复用编辑器实体的硬限制。需 macOS 实测「跳过 parse 但新建实体」是否仍触发。若不行，退化为「仅后台预热 parse 结果」有限收益版本。
- **优化 E（虚拟化）的黑屏 bug**：既有脆弱点（stride 估算过大导致 ghost-scroll）。下调阈值前必须修健估算并充分回归。
- **优化 F（DocumentTree 增量）**：移植核心代码，改动大、回归风险高，放后期。
- **redb/Tantivy 体积**：增加二进制体积（Tantivy 较大）。可设为可选 feature（仅大规模场景启用），或全量集成。
- **中文分词**：Tantivy 默认分词器对中文不理想，需配中文 tokenizer（如 jieba 集成或按字符分词）。首期可用「按字符分词」保证 substring 匹配，后续优化。

## 十二、编码规范（遵循 AGENTS.md）

- 索引访问一律 `.get(id)`，禁裸索引
- 字符串小写化结果缓存到 Tantivy 索引，避免每搜索重复分配
- 生产代码禁 `unwrap()`（索引未命中返回空/None 静默跳过）
- UI 回调入口（搜索、select）校验索引在界内
- redb/Tantivy 写入用各自事务 API；`.md` 仍是原子写（`.tmp` + `rename`）
- 索引重建走后台线程，避免阻塞 UI
